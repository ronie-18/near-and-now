# Near & Now — Full Codebase Deep Audit (2026-07-16, updated 2026-07-23)

Full-codebase pass across all 7 areas: `backend` (Express API), `frontend` (customer website), `admin` (admin panel), Supabase schema/migrations, and all three mobile apps (`near-now-store_owner`, `NAT_Near-Now_Rider-`, `nearandnowcustomerapp`). This supersedes/extends `supabase/SCHEMA_NOTES.md` (schema-focused). `bug_fixes_2026-07-15.md` (the original admin-approval-flow audit) has been merged into this file and deleted.

**Reading this doc:** `# Open Issues` comes first, grouped by area then severity, with each item's full original description so it's actionable without re-investigating. `# Fixed Issues` follows in compressed form (root cause + fix + date + any caveat that still matters, e.g. "not yet applied to the live DB") — enough to know what happened without the full investigation narrative. Reference material (pricing model, confirmed-not-bugs, build/test status, audit history) is at the very end.

# Open Issues

## Backend (`backend/src`)

### Low

- `auth.controller.ts:195,337` calls `crypto.randomUUID()` without importing `crypto` — works only because Node's global `crypto` happens to be available unprefixed; fragile across environments/bundlers.
- `notification.service.ts:113-117` `sendSMS` is a dead stub (`// TODO: Twilio / AWS SNS`) that always returns success without sending anything.
- `requireShopkeeper` blocks even read-only profile access for unapproved shopkeepers (`shopkeeper.controller.ts:30-71`) — a newly-signed-up shopkeeper can't check their own approval status.
- Expo push send calls never inspect per-message error responses — `delivery.controller.ts:232-241`, `shopkeeper.controller.ts:499-511,550-560` — stale/invalid tokens never get cleaned up, failures are invisible.
- Duplicate `declare module 'express'` Request augmentation in `invoice.controller.ts:9-15`, already redundant with 3 other files — the file's own comments document this exact duplication caused a real bug once before.
- `getNearbyStores` does a full table scan + JS-side haversine filter (found via QA-audit cross-check, 2026-07-16). `database.service.ts:283-298` — `select('*').eq('is_active', true)` over all stores, then filtered by distance in JS. No PostGIS/SQL-side geo filter, on a hot customer-facing path.
- **`getProductsWithDetails()` queries a Postgres relation, `products_with_details`, that doesn't exist in the live database** (found 2026-07-26 while investigating the store-owner offline-toggle item). `database.service.ts:245-281` calls `supabase.from('products_with_details').select('*')`; confirmed live via `information_schema.tables` — zero rows for that name anywhere, and `pg_get_viewdef()` fails with `42P01: relation does not exist`. Its two callers, `GET /api/products/products` (`getProducts`) and `GET /api/products/:id` (`getProductById`) in `products.controller.ts`, both 500 on every real request — confirmed live via `curl` against the local backend (`{"error":"Failed to fetch products"}`). Not currently a live customer-impact bug: grepped every frontend/mobile app and found zero callers of either route — the actual customer-facing product-fetch path is `frontend/src/services/supabase.ts` querying the `products`/`master_products` tables directly, entirely bypassing this backend endpoint. Left unfixed since it's dead code with no callers; flagging in case anything is ever pointed at it, or the view was meant to exist and its migration was lost.
- Backend's `validateDocNumber` accepts (unvalidated) a `number` field submitted alongside an `aadhaar_back`/`pan_back` upload, same as it already does for `trade` — harmless today since the app never sends one for back-side docs, but the backend doesn't actively reject one either.

# Fixed Issues

## Backend (`backend/src`)

### Critical

- **`supabaseAdmin` silently fell back to the anonymous client when the service-role key was missing/malformed.** Any of ~108 call sites expecting service-role RLS bypass would instead silently run as `anon`, degrading into confusing empty-result/permission-denied bugs. **Fixed 2026-07-24** by replacing the anon fallback with a `Proxy` that throws a clear error the instant anything actually tries to use it, closing the gap for every call site at once without touching them individually.
- **`requireRider` never checked `is_approved` on `rejectOrder`/`markPickedUp`/`markDelivered`** (only `acceptOrder`/`acceptOffer` did), so a just-signed-up unapproved rider could still call them. **Fixed 2026-07-23** with a new `requireApprovedRider(riderId)` helper called at the top of all three, mirroring `acceptOrder`'s existing 403 response.
- **Anon-callable RPC `finalize_order_if_ready` had no caller-identity check.** Migration `20260720000000` had granted `EXECUTE` to `anon`; this `SECURITY DEFINER` function bypasses RLS and could force-advance any order to `ready_for_pickup` before any store accepted it. **Fixed 2026-07-23** by revoking `anon`/`authenticated` execute grants (`20260810000000_lock_down_anon_rpc_grants.sql`, applied to the live DB).
- **No ownership check on order-mutating rider endpoints.** **Fixed 2026-07-16** — `acceptOrder` now atomically claims only unassigned orders; `rejectOrder`/`markPickedUp`/`markDelivered` now filter by `assigned_driver_id === req.riderId`.
- **`processRefund` had zero authentication.** **Fixed 2026-07-16** — `/refund` now requires `requireAdmin`. (`/methods` and `/:paymentId` on the same router are still open — see Backend High → Fixed for the PII-leak scope of that router.)
- **`placeCheckoutOrder` trusted client-supplied prices/total/payment_status** — the `order_total: 1, payment_status: "paid"` exploit. **Fixed 2026-07-16** — item prices are recomputed server-side from `master_products` (GST-aware, per the two-layer pricing model), `subtotal_amount` is recomputed from those trusted prices, `order_total` is floor-checked, and `payment_status` is always inserted as `'pending'`, only flippable via the signature-verified payment-verify path.
- **`signupComplete` (store owner + delivery partner) never verified OTP was actually completed.** **Fixed 2026-07-16** with a signed, short-lived HMAC "signup ticket" issued by `verifyOTP` and required by both `signupComplete` handlers.

Verified live against the real anon-key REST API: direct `expo_push_token` select and `select=*` both now correctly 401 with "permission denied for table stores," the explicit safe-column list still returns real data, and the new RPC correctly rejects a call with no admin session header ("Not authorized").

## Reference: Pricing Model / GST

Confirmed by product owner, 2026-07-16. Two independent, stacking GST layers — needed context for anything touching prices, checkout totals, or invoices:

1. **Per-item GST**, baked into each product's sellable price: `item_price = master_products.discounted_price + (discounted_price × master_products.gst_rate / 100)`. `discounted_price` is the pre-tax base. `is_loose = true` (loose/weighed products) → `gst_rate` is always 0. `is_loose = false` (packaged products) → follow the `gst_rate` column. Reference implementation: `frontend/src/utils/priceGst.ts`, mirrored in `admin/src/utils/priceGst.ts` and `frontend/src/services/supabase.ts:206-221`.
2. **A separate flat 5% GST on the whole bill at checkout**, mandated by GoI as a business-level tax (the rate can change if GoI changes it) — applied on top of the already-GST-inclusive item subtotal. This is intentional, not double taxation (see Confirmed Not Bugs below). Implemented in `frontend/src/utils/checkoutCalculations.ts`.

Any server-side price/total recomputation must replicate both layers or it will silently diverge from what the customer actually saw and agreed to pay.
