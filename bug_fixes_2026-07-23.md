# Near & Now — Full Codebase Deep Audit (2026-07-16, updated 2026-07-23)

Full-codebase pass across all 7 areas: `backend` (Express API), `frontend` (customer website), `admin` (admin panel), Supabase schema/migrations, and all three mobile apps (`near-now-store_owner`, `NAT_Near-Now_Rider-`, `nearandnowcustomerapp`). This supersedes/extends `supabase/SCHEMA_NOTES.md` (schema-focused). `bug_fixes_2026-07-15.md` (the original admin-approval-flow audit) has been merged into this file and deleted.

**Reading this doc:** `# Open Issues` comes first, grouped by area then severity, with each item's full original description so it's actionable without re-investigating. `# Fixed Issues` follows in compressed form (root cause + fix + date + any caveat that still matters, e.g. "not yet applied to the live DB") — enough to know what happened without the full investigation narrative. Reference material (pricing model, confirmed-not-bugs, build/test status, audit history) is at the very end.

# Open Issues

## Backend (`backend/src`)

### Medium

- `tracking_events` table is fully dead — zero insert call sites anywhere in `backend/src` (found via QA-audit cross-check, 2026-07-16). Confirmed via full grep — the table exists in migrations and a route theoretically supports it, but only `order_status_history` is actually written. Misleading for anyone building against this table expecting it to be populated.
- `getAgentSchedule` ignores its parameters and always returns `[]` (found via QA-audit cross-check, 2026-07-16) — a stub, not wired to any real schedule data.

### Low

- `auth.controller.ts:195,337` calls `crypto.randomUUID()` without importing `crypto` — works only because Node's global `crypto` happens to be available unprefixed; fragile across environments/bundlers.
- `notification.service.ts:113-117` `sendSMS` is a dead stub (`// TODO: Twilio / AWS SNS`) that always returns success without sending anything.
- `requireShopkeeper` blocks even read-only profile access for unapproved shopkeepers (`shopkeeper.controller.ts:30-71`) — a newly-signed-up shopkeeper can't check their own approval status.
- Expo push send calls never inspect per-message error responses — `delivery.controller.ts:232-241`, `shopkeeper.controller.ts:499-511,550-560` — stale/invalid tokens never get cleaned up, failures are invisible.
- Duplicate `declare module 'express'` Request augmentation in `invoice.controller.ts:9-15`, already redundant with 3 other files — the file's own comments document this exact duplication caused a real bug once before.
- `getProductById` fetches the entire product catalog then `.find()`s in JS (found via QA-audit cross-check, 2026-07-16). `products.controller.ts:51-66` — `databaseService.getProductsWithDetails()` (no filter) then linear-scans for the one product. Latency/cost concern as the catalog grows.
- `getNearbyStores` does a full table scan + JS-side haversine filter (found via QA-audit cross-check, 2026-07-16). `database.service.ts:283-298` — `select('*').eq('is_active', true)` over all stores, then filtered by distance in JS. No PostGIS/SQL-side geo filter, on a hot customer-facing path.
- `getProductsWithDetails` does the same full-scan + JS-side radius filter (found via QA-audit cross-check, 2026-07-16). `database.service.ts:245-281` — queries unfiltered by location, then filters by `calculateDistance()` in JS when a radius is requested.
- Backend's `validateDocNumber` accepts (unvalidated) a `number` field submitted alongside an `aadhaar_back`/`pan_back` upload, same as it already does for `trade` — harmless today since the app never sends one for back-side docs, but the backend doesn't actively reject one either.

If the session insert silently fails, the UI hands back a token that *looks* valid but has no corresponding DB row — every subsequent `is_admin_authenticated()` check fails, and the admin appears logged in while every real page shows empty data (this is precisely the failure mode already root-caused and fixed once on 2026-07-15 for the *first* login after that fix — this finding is about the same class of bug being able to recur silently for any future login where the insert happens to fail).

If ever run outside a browser context, throws and silently drops the audit-log write (caught by an outer try/catch, but the security event is lost).
- `getCustomers` returns all `app_users` rows with no role filter (found via QA-audit cross-check, 2026-07-16). `adminService.ts:703-706`, no `.eq('role', 'customer')` — non-customer roles would leak into the Customers list/count if `app_users` ever holds them in a way that matters.
- Status mapping collapses order statuses into 5 states (found via QA-audit cross-check, 2026-07-16). `mapDbStatusToFrontend`, `adminService.ts:447-454` — e.g. `preparing_order` and `ready_for_pickup` both collapse to `'confirmed'`, losing operationally-relevant granularity in the admin UI.
- `updateOrderStatus` (admin) can never explicitly set `preparing_order` (found via QA-audit cross-check, 2026-07-16 — distinct from the already-documented missing state-machine-validation bug in the same function). `adminService.ts:662-668` maps `confirmed` → `store_accepted`, skipping over `preparing_order` entirely.
- Admin session stored in `sessionStorage` only, no persistent option (found via QA-audit cross-check, 2026-07-16). `AdminLoginPage.tsx:46-48` — closing the tab silently logs the admin out.
- `SettingsPage` notification/appearance prefs are localStorage-only, don't follow the admin across devices (found via QA-audit cross-check, 2026-07-16). `SettingsPage.tsx` (`NOTIF_PREFS_KEY` lines ~215-268, `DISPLAY_PREFS_KEY` lines ~272-339) — only the Account/password tab does a real DB write via `updateAdmin()`.
- Admin's 3 new notification types don't surface `notif.data` (`store_id`/`doc_type`) anywhere in `NotificationsPage.tsx`'s list UI — only `refund_required` gets that treatment today. UX gap, not a defect.

- Admin email/role/error-stack details logged to console on every login attempt, uncompressed for production.
- `services/supabase.ts` inside the *admin* app contains a large amount of customer-facing logic (`createOrder`, `getUserOrders`, newsletter, address CRUD) that's dead weight in the admin bundle — looks like a stale copy-paste from the customer-facing frontend.
- `sessionStorage['adminData']` parsed with raw, uncaught `JSON.parse` in 3 components instead of the shared `getCurrentAdmin()` helper (found via QA-audit cross-check, 2026-07-16). `CreateAdminPage.tsx:33-34`, `EditAdminPage.tsx:38-39`, `AdminManagementPage.tsx:125-126` — any corruption/tampering of that storage key crashes these pages with an unhandled exception instead of failing gracefully.

## Supabase schema & migrations

### Medium

- No DB-level enforcement forcing `stores.is_active` back to `false` if admin revokes `stores.is_approved` on an already-online store (from 2026-07-15 audit). The rider side has an equivalent trigger (`20260428000001_decouple_is_online_from_status.sql`, forces `is_online = false` whenever `status <> 'active'`) — the store side has no matching trigger, so a store stays online until the shopkeeper (or some future toggle attempt) happens to touch the row.

### Low / informational

- The `coupons`/`product_images`/`product_attributes`/`product_details` grants added on 2026-07-18 (`SELECT` to `anon`/`authenticated` while RLS stays disabled on those tables) is exactly the trap `SCHEMA_NOTES.md` itself warns about — appears deliberate and carefully scoped (non-PII columns only, `product_reviews` explicitly excluded for its PII columns), but worth a second confirmation pass that RLS staying disabled there is intentional, and updating SCHEMA_NOTES to note the trap has since been (carefully) sprung rather than just theoretical.
- Two of three previously-dead RLS policies (`customer_own_orders`, `customer_own_record`) are still permanently dead code — they gate on `auth.uid()`, but the customer app doesn't use Supabase Auth (uses its own phone-OTP JWT), so `auth.uid()` is always NULL from that frontend, documented in an unrelated migration's own comment. Not exploitable (fails closed), but misleading — a future developer could believe there's a working customer-self-access RLS path when there isn't. **Consequence confirmed 2026-07-23:** the customer mobile app's Order Detail screen (`app/order/[id].tsx`) relies on exactly this dead `customer_own_orders` policy for its realtime subscription and has no polling fallback at all — see Customer app → Medium (new). **The third, `partner_own_record` on `delivery_partners`, is no longer dead** — see Rider app → High (fixed 2026-07-25): the backend now mints riders a real Supabase Auth bridge session specifically so this policy has a working `auth.uid()` to evaluate.
- `stores.public_read` (`USING (true)`) exposes every column on the row, not just the ones a customer/rider actually needs (found 2026-07-25, while explaining the stores-vs-delivery_partners realtime tradeoff to the user). RLS is row-level, not column-level — `name`/`address`/`phone`/`latitude`/`longitude`/`image_url`/`is_active`/`is_approved` being public is intentional and fine, but `expo_push_token` rides along on the same policy and wasn't meant to be public. Since Expo's push-send API doesn't authenticate the sender, anyone holding the app's anon key can currently read any store's push token and use it to send arbitrary push notifications to that shopkeeper's device, impersonating the app. Low severity (no PII/financial exposure, just notification spam/impersonation potential), but worth closing — usual fix is a Postgres view over `stores` that excludes `expo_push_token` for the public-facing read path, or moving the token to a separate backend/admin-only table. **Deliberately not fixed yet** — logged for the dedicated security-focused pass.

## Store-owner app (`near-now-store_owner`)

### Medium

- Realtime channel names include `Date.now()` (`home.tsx:216,223`), causing churn on every store-selection/re-render instead of reusing/deduping channels — confirmed still present from a prior audit.
- Client-side "auto-complete order after 2 minutes" logic (`previous-orders.tsx:285-305`) only runs while the app happens to be open and polling — if the shopkeeper backgrounds/closes the app, orders can be stuck un-completed indefinitely; this should be a server-side scheduled job, not client-triggered.
- Two entirely dead-code order-management implementations exist in parallel with the real one: `hooks/useOrders.ts` + `components/IncomingOrderPopup.tsx` (a more complete 60s-auto-reject flow, never wired in) and `lib/order-service.ts` + `components/OrderFilters.tsx` (targets a `/store-owner/orders/*` API contract that doesn't match the real `/shopkeeper/allocations/*` endpoints in use — would silently fail if ever revived).
- `context/AppContext.tsx` and `lib/testSupabase.ts` (including a function that performs live inserts/deletes against the real `products` table) are both entirely dead/unreferenced code.
- Store images support only a single image, no carousel/array (found via QA-audit cross-check, 2026-07-16). `lib/storage.ts:71-77` `uploadStoreImage()` uses a fixed path (`${storeId}/cover.${ext}`) and returns a single result; `app/profile.tsx:53` holds only one `storeImageUri` state value. Real product-completeness gap for customer-facing store listings.
- No admin notification on profile-edit click (24h approval workflow) (found via QA-audit cross-check, 2026-07-16). Zero matches anywhere in the repo for a `profile_change_request` concept or any admin-notify call in `app/profile.tsx`. Profile edits take effect with no admin review trail.
- `toggleStoreStatus` is implemented three separate times, only one is actually wired to the UI (found via QA-audit cross-check, 2026-07-16). `lib/store-service.ts:146`, `hooks/useStore.ts:75`, and an inline copy in `app/(tabs)/home.tsx:252-275` (renamed `toggleOnline`, the only one actually called by `handleStatusToggle`/`StoreStatusCard`). A fix applied to either of the two unused implementations would silently never take effect — real regression risk for future maintainers editing the "obvious" file.
- `setAllProductsOffline`/`restoreActiveProductsOnline` are silent no-ops called unconditionally in the online-toggle critical path (found via QA-audit cross-check, 2026-07-16). `lib/storeProducts.ts:436-438,444-446` both return `true` unconditionally (comment: "no-op now that quantity/in_stock are removed"), yet are still awaited unconditionally in `app/(tabs)/home.tsx:260,267` on every toggle. Toggling a store offline gives shopkeepers the false impression that product visibility actually changes when nothing happens server-side.
- `lib/orders-db.ts` has a silent 4-strategy fallback chain, all failures swallowed to `console.warn`, none surfaced to the UI (found via QA-audit cross-check, 2026-07-16). `getOrdersFromDb()` cascades RPC → direct-table (90-day/100-row cap) → `customer_orders` fallback, imported by `previous-orders.tsx`, `invoice/[orderId].tsx`, `payments.tsx`. An RLS misconfiguration or RPC failure degrades silently into an indistinguishable "no orders" empty state.
- App's own `supabase/*.sql` scripts are tracked in git but aren't real Supabase-CLI migrations — unverifiable whether ever applied to the live DB (found via QA-audit cross-check, 2026-07-16). Confirmed tracked via `git ls-files supabase/` (contradicting an earlier claim they were untracked), but there's still no `supabase/migrations/` directory or `config.toml` in this repo — several live code paths (RLS policies, RPC functions referenced by the `orders-db.ts` fallback chain above) depend on these having actually been run against production, with no static way to confirm.
- Generic error message on accept-conflict — partially addressed 2026-07-24 re-verification. `hooks/useOrders.ts:170` still shows the pure generic message, but `app/(tabs)/previous-orders.tsx:398` now surfaces `json?.error || response.error || "Failed to accept order"` instead of a flat generic string. Doesn't fully close the gap yet: the backend does send a differentiated 409 message (`shopkeeper.controller.ts`, `"Already responded: ..."`) under the field name `error`, but `lib/api-client.ts`'s `getErrorMessage()` only reads `error.data.message` — so on a real 409 the app still falls through to a generic HTTP status text (e.g. "Conflict") rather than the specific "already responded" text. A shopkeeper who loses the race now sees *some* differentiation by status code, but not the clear message they'd need.

### Low

- Several silent `catch {}` blocks in approval-check/session flows (already partly known/intentional, re-confirmed present).
- Heavy unconditional `console.log`/`warn`/`error` in `lib/notifications.ts`, not gated behind `__DEV__`, including full notification payload contents.
- `scheduleNotification()`'s `_triggerDate` parameter is entirely ignored — always fires immediately regardless of what's passed, misleading if a "daily summary" feature (listed as a settings option with no backing implementation) is ever built on top of it.
- `isActivated` field defaults to `true` when missing from the server response (from 2026-07-15 audit) — fail-open, though it currently only affects a profile-page label, not access control.

## Rider app (`NAT_Near-Now_Rider-`)

### Medium

- Double-tap on "Accept offer" can fire two concurrent accept requests before React's `disabled` state re-render lands — no `useRef` in-flight lock, only async state (server-side atomicity likely prevents double-award, but produces duplicate network calls/alerts/navigations).
- A realtime-channel subscribe/teardown race (`home.tsx:321-356`) can orphan a Supabase channel subscription if `isOnline` toggles quickly between the effect running and its async session-fetch resolving — leads to duplicated haptic buzzes/fetches for new offers over a session.
- "Ignore offer" is client-state-only, unpersisted — resets on any app restart, so a previously-ignored offer can reappear.
- Active-order poll runs every 6s regardless of online/offline status (found via QA-audit cross-check, 2026-07-16). `app/(tabs)/home.tsx:319-342` — gated only on `!token`, unconditionally calls `fetchActiveOrder()` + `setInterval(fetchActiveOrder, 6000)`. Only the *offers* poll is gated on `isOnline`; a code comment justifies the active-order poll running regardless ("a simulation or manual dispatch can assign an order even when offline"), but it still means unnecessary battery/network drain for riders who are deliberately offline.
- No admin notification/audit trail on rider profile-edit requests (found via QA-audit cross-check, 2026-07-16). `app/(tabs)/profile.tsx:212-244` (`handleSave`) does a direct `PATCH /delivery-partner/profile` with no request-tracking or admin-facing notification. Profile changes (name/email/address) take effect immediately with no admin visibility or approval workflow.
- Rider rating hardcoded at 4.8 (found via QA-audit cross-check, 2026-07-16). `app/(tabs)/profile.tsx:354` — literal `4.8`, no backend-sourced field. Displays a fabricated trust/quality signal that has no relation to actual performance.
- `vehicle_type`/`vehicle_number` still never rendered as text anywhere in the rider profile UI (narrowed 2026-07-24 re-verification — was "no vehicle type/image fields"; the image half is now fixed, see Fixed Issues). Backend returns `vehicle_number` but it's present only in the `Profile` type, unused in JSX anywhere in `app/(tabs)/profile.tsx` — still incomplete for riders/admins reviewing rider identity.
- Orders screen status badges mismatch what the backend actually emits (found via QA-audit cross-check, 2026-07-16). `app/(tabs)/orders.tsx:30-34` defines a badge for `en_route_delivery`, but `deliveryPartner.controller.ts`'s `mapDbStatusToRider()` (71-81) only ever returns `rider_assigned`/`picking_up`/`picked_up`/`completed` — `en_route_delivery` is dead, and `picking_up`/`picked_up` (which the backend does emit) have no badge config, falling through to unstyled generic rendering.
- No GPS accuracy or staleness check before sending a heartbeat/location update (found 2026-07-23). `app/(tabs)/home.tsx:216-235` — `sendLocation()` forwards whatever `accuracy` value the OS reports with no filtering (e.g. a 500m-accuracy cold-GPS-lock fix is sent as-is); `sendLastKnownLocation()` calls `Location.getLastKnownPositionAsync()` and forwards it unconditionally with no check against `loc.timestamp`, so an hours-old cached fix can be re-sent to the backend/customer-facing tracker as if it were current, with no rider-side warning.
- Order-offer push notifications are never persisted to the `notifications` table (found 2026-07-23). `backend/src/controllers/shopkeeper.controller.ts:610-632` (`dispatchReadyOrdersToDriver`) sends the Expo push directly without calling `persistNotification`, unlike `notifyRiderNewOrder`/`notifyShopkeeperNewOrder` in `notification.service.ts`, which both persist + push. If a rider dismisses/misses the push (app killed, DND, notification swiped away), there is no record of it in the in-app Notifications screen to catch up on later — the only way to see the offer is still being online and having it show up in the (up to 15s-delayed) offers poll.
- Home screen silently swallows repeated polling failures (found 2026-07-23). `app/(tabs)/home.tsx:284,299` — empty `catch {}` around `/available-orders`/`/orders?status=active` polling. A rider online during a degraded-but-reachable backend sees "No orders right now" with no indication polling is actually failing, rather than that there's genuinely no work.

### Low

- `lib/authService.ts` is entirely dead code (never imported), and its unused OTP functions log raw phone numbers and API URLs — latent PII-in-logs risk if ever wired back in.
- `components/MapViewWrapper.tsx` is unused dead weight — the app bundles `react-native-maps` and Google Maps keys for no actual in-app map usage (only deep-links out to the native Maps app).
- Same "state instead of ref for in-flight-request guard" pattern recurs in `otp.tsx`'s verify flow as in the accept-offer bug above — low-likelihood double-submit race.
- `isActivated` session field continues to be threaded through every session-save call site despite being confirmed dead/unused elsewhere — easy to mistake for the real approval gate.
- Hardcoded admin support phone number baked into `home.tsx` (from 2026-07-15 audit), rather than sourced from config.
- `driver_order_offers` anon realtime read relies on a client-supplied `driver_id` filter, not RLS scoping (found 2026-07-23, documented tradeoff — flagged for awareness, not a new exploit). `app/(tabs)/home.tsx:358-366`, `supabase/migrations/20260806000000_driver_order_offers_anon_read.sql` — RLS policy is unconditionally `USING (true)`; since the client subscribes with a plain anon-key client (no real Supabase Auth session) and its own `filter: 'driver_id=eq.${driverId}'`, any anon client can subscribe to any `driver_id`'s offer events by supplying that UUID. The migration's own comment documents this as an accepted tradeoff (no PII in that table) — worth tightening (e.g. Realtime Authorization keyed off a signed channel token) if revisited.

# Fixed Issues

## Backend (`backend/src`)

### Critical

- **`supabaseAdmin` silently fell back to the anonymous client when the service-role key was missing/malformed.** Any of ~108 call sites expecting service-role RLS bypass would instead silently run as `anon`, degrading into confusing empty-result/permission-denied bugs. **Fixed 2026-07-24** by replacing the anon fallback with a `Proxy` that throws a clear error the instant anything actually tries to use it, closing the gap for every call site at once without touching them individually.
- **`requireRider` never checked `is_approved` on `rejectOrder`/`markPickedUp`/`markDelivered`** (only `acceptOrder`/`acceptOffer` did), so a just-signed-up unapproved rider could still call them. **Fixed 2026-07-23** with a new `requireApprovedRider(riderId)` helper called at the top of all three, mirroring `acceptOrder`'s existing 403 response.
- **Anon-callable RPC `finalize_order_if_ready` had no caller-identity check.** Migration `20260720000000` had granted `EXECUTE` to `anon`; this `SECURITY DEFINER` function bypasses RLS and could force-advance any order to `ready_for_pickup` before any store accepted it. **Fixed 2026-07-23** by revoking `anon`/`authenticated` execute grants (`20260810000000_lock_down_anon_rpc_grants.sql`, applied to the live DB).
- **No ownership check on order-mutating rider endpoints.** **Fixed 2026-07-16** — `acceptOrder` now atomically claims only unassigned orders; `rejectOrder`/`markPickedUp`/`markDelivered` now filter by `assigned_driver_id === req.riderId`.
- **`processRefund` had zero authentication.** **Fixed 2026-07-16** — `/refund` now requires `requireAdmin`. (`/methods` and `/:paymentId` on the same router are still open — see Backend High → Fixed for the PII-leak scope of that router.)
- **`placeCheckoutOrder` trusted client-supplied prices/total/payment_status** — the `order_total: 1, payment_status: "paid"` exploit. **Fixed 2026-07-16** — item prices are recomputed server-side from `master_products` (GST-aware, per the two-layer pricing model), `subtotal_amount` is recomputed from those trusted prices, `order_total` is floor-checked, and `payment_status` is always inserted as `'pending'`, only flippable via the signature-verified payment-verify path.
- **`signupComplete` (store owner + delivery partner) never verified OTP was actually completed.** **Fixed 2026-07-16** with a signed, short-lived HMAC "signup ticket" issued by `verifyOTP` and required by both `signupComplete` handlers.
- **`POST /api/orders/place` had zero authentication, trusting `user_id` in the body.** **Fixed 2026-07-16** — now requires `requireCustomer`; `user_id` is always overwritten from the session.

### High

- **Shopkeeper signup crashed with a raw Postgres unique-constraint error on repeat phone.** Root cause: `stores.phone` had a `UNIQUE` constraint that conflicted with the real business model (one shopkeeper can own multiple stores on the same phone). **Fixed 2026-07-25** by dropping `stores_phone_key` (migration `20260816000000`) and returning friendly, detailed error messages (`describeSignupDbError`) instead of raw Postgres errors. Two same-session follow-ups: the friendly-generic-message version had to be made to specifically explain the known "migration not yet applied" case, and later expanded into a full technical-detail-plus-plain-English format per user request. Migration applied to the live DB same day.
- **Driver broadcast dispatch searched for nearby drivers relative to the customer's delivery address instead of the store/pickup location.** **Fixed 2026-07-24** — both `shopkeeper.controller.ts`'s auto-dispatch and `delivery.controller.ts`'s admin-manual broadcast now center the search on the order's actual pickup store instead of the drop-off address.
- **`deleteStoreProduct` had its own unfiltered role lookup (latent IDOR), unlike every other `storeOwner.controller.ts` handler.** **Fixed 2026-07-24** by routing it through the same shared `resolveShopkeeperFromToken()` helper the other 11 handlers already use.
- **Admin's `updateOrderStatus` had no state-machine validation** — could move a delivered order back to any earlier status, re-triggering customer notifications. **Fixed 2026-07-24** — rejects (409) any status change once an order is `order_delivered`/`order_cancelled`; also added the missing `picking_up` value to `validStatuses`.
- **`cancelOrder` had no order-status guard** — a delivered order could be "cancelled" and wrongly auto-refunded. **Fixed 2026-07-24** — throws if already delivered or already cancelled.
- **Shopkeeper "complete allocation" endpoint could mark an order delivered with no rider or OTP involved, and was silently auto-called on every real order 2 minutes after acceptance** (leftover simulation logic from before the real delivery flow existed) — could override a real in-progress delivery's status. **Fixed 2026-07-24** by removing the endpoint and the shopkeeper app's auto-call timer entirely; confirmed nothing else depends on it.
- **No approval notification when admin approves a store or rider.** Admin approval is a direct Supabase write from the admin panel, with no Node code path to hook into. **Fixed 2026-07-23** via two new admin-only backend endpoints that re-verify approval server-side and fire the notification (reusing the existing persist+push pattern), called fire-and-forget from the admin panel after the approve write succeeds.
- **`getNotificationPreferences`/`updateNotificationPreferences` were a hardcoded stub and, once fixed, would have been an IDOR** (trusted `req.params.userId` instead of session). **Fixed 2026-07-23** — new `app_users.notification_preferences JSONB` column, real read/write, scoped to `req.customerId`. **DB migration not yet applied to the live database.**
- **Unauthenticated `/api/orders/create` trusted client-supplied `unit_price`**, allowing arbitrary-priced orders attributed to any customer. **Fixed 2026-07-23** — now requires `requireCustomer`, derives `customer_id` from the session, and reprices every item server-side using the same GST-aware formula as `placeCheckoutOrder`.
- **Delivery/pickup OTP and pickup codes were brute-forceable** (no lockout on 4-digit codes). **Fixed 2026-07-16** (Jira SCRUM-14) — rate-limited to 3 attempts/3 minutes, keyed per rider+order.
- **Tracking endpoints leaked any order's address/driver PII to any logged-in customer** (no ownership check beyond "some valid customer"). **Fixed 2026-07-16** (Jira SCRUM-12) — all four `database.service.ts` tracking methods now verify the order belongs to the calling customer. Old tiered pricing preserved in git history to restore later.
- **Admin delivery-simulation could hijack a real, currently-busy rider's location/assignment** (found 2026-07-23). `deliverySimulation.service.ts`'s `findRealDriver()` picked any `delivery_partners` row at every fallback tier with no check for whether that rider was already `assigned_driver_id` on another real, non-terminal order — then overwrote their `driver_locations` row with fabricated GPS and reassigned them to the simulated order. **Fixed 2026-07-26** by adding a `getBusyDriverIds()` check (any driver who is `assigned_driver_id` on a different order not yet `order_delivered`/`order_cancelled`) and excluding those drivers at all three fallback tiers, not just the last one. ## Reference: Pricing Model / GST

Confirmed by product owner, 2026-07-16. Two independent, stacking GST layers — needed context for anything touching prices, checkout totals, or invoices:

1. **Per-item GST**, baked into each product's sellable price: `item_price = master_products.discounted_price + (discounted_price × master_products.gst_rate / 100)`. `discounted_price` is the pre-tax base. `is_loose = true` (loose/weighed products) → `gst_rate` is always 0. `is_loose = false` (packaged products) → follow the `gst_rate` column. Reference implementation: `frontend/src/utils/priceGst.ts`, mirrored in `admin/src/utils/priceGst.ts` and `frontend/src/services/supabase.ts:206-221`.
2. **A separate flat 5% GST on the whole bill at checkout**, mandated by GoI as a business-level tax (the rate can change if GoI changes it) — applied on top of the already-GST-inclusive item subtotal. This is intentional, not double taxation (see Confirmed Not Bugs below). Implemented in `frontend/src/utils/checkoutCalculations.ts`.

Any server-side price/total recomputation must replicate both layers or it will silently diverge from what the customer actually saw and agreed to pay.
