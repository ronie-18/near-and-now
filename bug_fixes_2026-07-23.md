# Open Issues

## Backend (`backend/src`)

### Low

- `auth.controller.ts:195,337` calls `crypto.randomUUID()` without importing `crypto` — works only because Node's global `crypto` happens to be available unprefixed; fragile across environments/bundlers.
- `notification.service.ts:113-117` `sendSMS` is a dead stub (`// TODO: Twilio / AWS SNS`) that always returns success without sending anything.
- `requireShopkeeper` blocks even read-only profile access for unapproved shopkeepers (`shopkeeper.controller.ts:30-71`) — a newly-signed-up shopkeeper can't check their own approval status.
- Expo push send calls never inspect per-message error responses — `delivery.controller.ts:232-241`, `shopkeeper.controller.ts:499-511,550-560` — stale/invalid tokens never get cleaned up, failures are invisible.
- Duplicate `declare module 'express'` Request augmentation in `invoice.controller.ts:9-15`, already redundant with 3 other files — the file's own comments document this exact duplication caused a real bug once before.
- `getNearbyStores` does a full table scan + JS-side haversine filter (found via QA-audit cross-check, 2026-07-16). `database.service.ts:283-298` — `select('*').eq('is_active', true)` over all stores, then filtered by distance in JS. No PostGIS/SQL-side geo filter, on a hot customer-facing path.
- **`getProductsWithDetails()` queries a Postgres relation, `products_with_details`, that doesn't exist in the live database** (found 2026-07-26 while investigating the store-owner offline-toggle item). `database.service.ts:245-281` calls `supabase.from('products_with_details').select('*')`; confirmed live via `information_schema.tables` — zero rows for that name anywhere, and `pg_get_viewdef()` fails with `42P01: relation does not exist`. Its two callers, `GET /api/products/products` (`getProducts`) and `GET /api/products/:id` (`getProductById`) in `products.controller.ts`, both 500 on every real request — confirmed live via `curl` against the local backend (`{"error":"Failed to fetch products"}`). Not currently a live customer-impact bug: grepped every frontend/mobile app and found zero callers of either route — the actual customer-facing product-fetch path is `frontend/src/services/supabase.ts` querying the `products`/`master_products` tables directly, entirely bypassing this backend endpoint. Left unfixed since it's dead code with no callers; flagging in case anything is ever pointed at it, or the view was meant to exist and its migration was lost.
- Backend's `validateDocNumber` accepts (unvalidated) a `number` field submitted alongside an `aadhaar_back`/`pan_back` upload, same as it already does for `trade` — harmless today since the app never sends one for back-side docs, but the backend doesn't actively reject one either.

## Supabase schema & migrations

### Critical

- **`app_users` has a live, currently-exploitable RLS hole: full anonymous read/write access, including `session_token`.** Found 2026-07-27 while deep-diving the `getCurrentUserFromSession` fix (Website frontend). A policy named `"Allow all for service role"` (`cmd: ALL`, `qual: true`) is scoped to `roles: {public}` instead of `{service_role}` — its name and `true` qualifier make the intent obvious (a service-role bypass), but because the role list was never actually restricted, it grants the same unconditional access to **every role**, including `anon`. Confirmed live via a plain `curl` with only the public anon key and no session/auth header at all: successfully read a real customer's `name`/`email`, and confirmed `session_token` is also selectable the same way — meaning any active customer's session can be hijacked by anyone holding the (intentionally public) anon key, just by reading their token off this table. This makes the existing "dead RLS policy, not exploitable (fails closed)" note below **incorrect** — `customer_own_record`'s own condition being permanently false (`auth.uid()` always NULL for this app) is irrelevant, since this separate misconfigured policy bypasses RLS checking entirely regardless. **Not fixed — flagged to the user immediately on discovery; explicitly asked to hold off touching production RLS for now.** Recommended fix when authorized: correct the policy's `roles` to `{service_role}` (matching its name and evident intent), applied via a migration and verified live the same way it was found (re-run the same anon `curl`, confirm denial).
- **Direct consequence, found the same session: the website's own Profile "Save Changes" write path (`services/authService.ts`'s `updateCustomerProfile`) is silently broken for address fields, and only "succeeds" for name/email because of the hole above, not by design.** The function writes directly from the browser via the anon-key Supabase client (never routed through the backend, unlike almost everything else fixed in this session) to two tables: `app_users` (name/email) and `customers` (surname/address/city/state/pincode/landmark/delivery_instructions). Confirmed live: `customers` has **zero** anon/authenticated grants at all (a `permission denied for table customers` 401, not just an RLS-empty-result) — so every address-field save has always failed outright, and the code never checks that write's result at all, so this failure has always been completely silent. The `app_users` half (name/email) *does* currently succeed — but only as an unintended side effect of the exact same misconfigured `{public}`-scoped policy above, not because this write path is actually sound. Before this session's `getCurrentUserFromSession` fix, the always-broken re-fetch masked all of this with an optimistic local merge, so the customer always saw their intended change reflected regardless of what actually persisted. **After the fix, an address-field save will now visibly and silently revert in the UI** (the real re-fetch correctly returns the old, unchanged address) with no error message telling the customer their save didn't take. **Not fixed — same reasoning as above:** the real fix (routing this write through an authenticated backend endpoint, matching the `PATCH /api/customers/me` pattern the mobile app and now `getCurrentUserFromSession` already use) is entangled with the RLS decision above and wasn't authorized this session. Flagging as a real, currently-live regression risk from the `getCurrentUserFromSession` fix specifically, even though the underlying breakage predates it.

### Low / informational

- The `coupons`/`product_images`/`product_attributes`/`product_details` grants added on 2026-07-18 (`SELECT` to `anon`/`authenticated` while RLS stays disabled on those tables) is exactly the trap `SCHEMA_NOTES.md` itself warns about — appears deliberate and carefully scoped (non-PII columns only, `product_reviews` explicitly excluded for its PII columns), but worth a second confirmation pass that RLS staying disabled there is intentional, and updating SCHEMA_NOTES to note the trap has since been (carefully) sprung rather than just theoretical.
- Two of three previously-dead RLS policies (`customer_own_orders`, `customer_own_record`) are still permanently dead code — they gate on `auth.uid()`, but the customer app doesn't use Supabase Auth (uses its own phone-OTP JWT), so `auth.uid()` is always NULL from that frontend, documented in an unrelated migration's own comment. **Correction 2026-07-27: the "not exploitable (fails closed)" claim below no longer holds** — see Critical above; a separate misconfigured policy on `app_users` bypasses RLS checking for that table regardless of whether `customer_own_record` itself ever evaluates true. Misleading either way — a future developer could believe there's a working customer-self-access RLS path when there isn't. **Consequence confirmed 2026-07-23:** the customer mobile app's Order Detail screen (`app/order/[id].tsx`) relies on exactly this dead `customer_own_orders` policy for its realtime subscription and has no polling fallback at all — see Customer app → Medium (new). **The third, `partner_own_record` on `delivery_partners`, is no longer dead** — see Rider app → High (fixed 2026-07-25): the backend now mints riders a real Supabase Auth bridge session specifically so this policy has a working `auth.uid()` to evaluate.

# Fixed Issues

## Backend (`backend/src`)

### Critical

- **`supabaseAdmin` silently fell back to the anonymous client when the service-role key was missing/malformed.** Any of ~108 call sites expecting service-role RLS bypass would instead silently run as `anon`, degrading into confusing empty-result/permission-denied bugs. **Fixed 2026-07-24** by replacing the anon fallback with a `Proxy` that throws a clear error the instant anything actually tries to use it, closing the gap for every call site at once without touching them individually.
- **`requireRider` never checked `is_approved` on `rejectOrder`/`markPickedUp`/`markDelivered`** (only `acceptOrder`/`acceptOffer` did), so a just-signed-up unapproved rider could still call them. **Fixed 2026-07-23** with a new `requireApprovedRider(riderId)` helper called at the top of all three, mirroring `acceptOrder`'s existing 403 response.
- **Anon-callable RPC `finalize_order_if_ready` had no caller-identity check.** Migration `20260720000000` had granted `EXECUTE` to `anon`; this `SECURITY DEFINER` function bypasses RLS and could force-advance any order to `ready_for_pickup` before any store accepted it. **Fixed 2026-07-23** by revoking `anon`/`authenticated` execute grants (`20260810000000_lock_down_anon_rpc_grants.sql`, applied to the live DB).
- **No ownership check on order-mutating rider endpoints.** **Fixed 2026-07-16** — `acceptOrder` now atomically claims only unassigned orders; `rejectOrder`/`markPickedUp`/`markDelivered` now filter by `assigned_driver_id === req.riderId`.
- **`processRefund` had zero authentication.** **Fixed 2026-07-16** — `/refund` now requires `requireAdmin`. (`/methods` and `/:paymentId` on the same router are still open — see Backend High → Fixed for the PII-leak scope of that router.)
- **`placeCheckoutOrder` trusted client-supplied prices/total/payment_status** — the `order_total: 1, payment_status: "paid"` exploit. **Fixed 2026-07-16** — item prices are recomputed server-side from `master_products` (GST-aware, per the two-layer pricing model), `subtotal_amount` is recomputed from those trusted prices, `order_total` is floor-checked, and `payment_status` is always inserted as `'pending'`, only flippable via the signature-verified payment-verify path.
- **`signupComplete` (store owner + delivery partner) never verified OTP was actually completed.** **Fixed 2026-07-16** with a signed, short-lived HMAC "signup ticket" issued by `verifyOTP` and required by both `signupComplete` handlers.
- **`POST /api/orders/place` had zero authentication, trusting `user_id` in the body.** **Fixed 2026-07-16** — now requires `requireCustomer`; `user_id` is always overwritten from the session.

### High

- **Shopkeeper signup crashed with a raw Postgres unique-constraint error on repeat phone.** Root cause: `stores.phone` had a `UNIQUE` constraint that conflicted with the real business model (one shopkeeper can own multiple stores on the same phone). **Fixed 2026-07-25** by dropping `stores_phone_key` (migration `20260816000000`) and returning friendly, detailed error messages (`describeSignupDbError`) instead of raw Postgres errors. Two same-session follow-ups: the friendly-generic-message version had to be made to specifically explain the known "migration not yet applied" case, and later expanded into a full technical-detail-plus-plain-English format per user request. Migration applied to the live DB same day.
- **Driver broadcast dispatch searched for nearby drivers relative to the customer's delivery address instead of the store/pickup location.** **Fixed 2026-07-24** — both `shopkeeper.controller.ts`'s auto-dispatch and `delivery.controller.ts`'s admin-manual broadcast now center the search on the order's actual pickup store instead of the drop-off address.
- **`deleteStoreProduct` had its own unfiltered role lookup (latent IDOR), unlike every other `storeOwner.controller.ts` handler.** **Fixed 2026-07-24** by routing it through the same shared `resolveShopkeeperFromToken()` helper the other 11 handlers already use.
- **Admin's `updateOrderStatus` had no state-machine validation** — could move a delivered order back to any earlier status, re-triggering customer notifications. **Fixed 2026-07-24** — rejects (409) any status change once an order is `order_delivered`/`order_cancelled`; also added the missing `picking_up` value to `validStatuses`.
- **`cancelOrder` had no order-status guard** — a delivered order could be "cancelled" and wrongly auto-refunded. **Fixed 2026-07-24** — throws if already delivered or already cancelled.
- **Shopkeeper "complete allocation" endpoint could mark an order delivered with no rider or OTP involved, and was silently auto-called on every real order 2 minutes after acceptance** (leftover simulation logic from before the real delivery flow existed) — could override a real in-progress delivery's status. **Fixed 2026-07-24** by removing the endpoint and the shopkeeper app's auto-call timer entirely; confirmed nothing else depends on it. (An Open Issues entry describing this same client-only timer as "should be a server-side scheduled job instead" survived as a stale duplicate until 2026-07-27, when a fresh grep of `previous-orders.tsx` found no timer/auto-complete logic left anywhere in the app — removed rather than re-fixed.)
- **No approval notification when admin approves a store or rider.** Admin approval is a direct Supabase write from the admin panel, with no Node code path to hook into. **Fixed 2026-07-23** via two new admin-only backend endpoints that re-verify approval server-side and fire the notification (reusing the existing persist+push pattern), called fire-and-forget from the admin panel after the approve write succeeds.
- **`getNotificationPreferences`/`updateNotificationPreferences` were a hardcoded stub and, once fixed, would have been an IDOR** (trusted `req.params.userId` instead of session). **Fixed 2026-07-23** — new `app_users.notification_preferences JSONB` column, real read/write, scoped to `req.customerId`. **DB migration not yet applied to the live database.**
- **Unauthenticated `/api/orders/create` trusted client-supplied `unit_price`**, allowing arbitrary-priced orders attributed to any customer. **Fixed 2026-07-23** — now requires `requireCustomer`, derives `customer_id` from the session, and reprices every item server-side using the same GST-aware formula as `placeCheckoutOrder`.
- **Delivery/pickup OTP and pickup codes were brute-forceable** (no lockout on 4-digit codes). **Fixed 2026-07-16** (Jira SCRUM-14) — rate-limited to 3 attempts/3 minutes, keyed per rider+order.
- **Tracking endpoints leaked any order's address/driver PII to any logged-in customer** (no ownership check beyond "some valid customer"). **Fixed 2026-07-16** (Jira SCRUM-12) — all four `database.service.ts` tracking methods now verify the order belongs to the calling customer. A related gap in `getAgentLocation` (no relationship check between caller and requested rider) was **fixed 2026-07-23**.
- **Riders could spoof another rider's GPS / write arbitrary order status** — `updateAgentLocation` didn't check `agentId === req.riderId`, and `addTrackingUpdate` accepted any string as status with no ownership check. **Fixed 2026-07-24** — location update now 403s on mismatch; status update validates against the real enum and checks `assigned_driver_id`.

### Medium

- **Tip was not independently verified server-side, and wasn't even a real structured field** — the website folded it into `order_total` untraced, the customer app's tip was silently dropped by an undeclared schema field. **Fixed 2026-07-25** as part of building the first real rider payout system: new `tip_amount` column, accepted/stored/verified end-to-end, and folded into the trusted floor check (`20260818000000_tip_amount_and_rider_payouts.sql`). See Rider app Medium for the payout side.
- **Coupon discount was validated but never actually computed, enforced, or persisted at checkout** — `discount_amount` was hardcoded `0` everywhere, and `placeCheckoutOrder` didn't even accept a `coupon_id`. **Fixed 2026-07-23** across backend + both frontends — new `computeCouponDiscount()` helper (flat/percent/first-order rules, capped and clamped), real persistence, `recordCouponUsage` now fires from the real checkout path, and the trusted-total floor check subtracts the discount. Website got a coupon UI built from scratch (it had none). **Not click-tested live in a real browser** — verified via `tsc`, test suites, and a prod build pass only.
- **`acceptOffer`'s post-RPC follow-up writes were redundant, duplicate updates** left over from before `accept_driver_offer()` was rewritten to already do them atomically. **Fixed 2026-07-23** by removing the dead duplicate writes.
- **Coupon `usage_count` increment was a non-atomic read-then-write race**, letting concurrent redemptions push a coupon past its usage limit. **Fixed 2026-07-23** via a new row-locking Postgres function (`increment_coupon_usage_if_available`), migration applied to the live DB.
- **`GET /api/coupons/` returned every coupon with no way to tell at a glance which were currently valid.** **Fixed 2026-07-23** by attaching a computed `is_currently_valid` boolean to each row rather than filtering rows out (admin needs to see expired/inactive coupons too).
- **Admin-facing coupon/delivery-partner endpoints had no schema validation.** **Fixed 2026-07-23** — added Zod schemas wired through the existing `validate()` middleware, same pattern as `orders.routes.ts`.
- **Google Places/Geocoding/Directions proxy was fully public with no rate limiting** (billing-DoS risk). **Fixed 2026-07-23** — 60 requests/minute per IP via `express-rate-limit`.
- **`express.json()` had no explicit body size limit.** **Fixed 2026-07-23** — capped at 1MB with a clean 413 response instead of a generic 500.
- **`getOrderById` returned 500 instead of 404 for a non-existent order** (`.single()` throws on no match). **Fixed 2026-07-23** by switching to `.maybeSingle()`.
- **Three independent haversine/distance implementations existed in the backend.** **Fixed 2026-07-23** — consolidated into `backend/src/utils/geo.ts`.
- **`delivery_fee` was not independently verified server-side.** **Fixed 2026-07-23** as a business decision — delivery is ₹0 for now (launch-goodwill promo); backend, website, and the legacy `createOrder` fallback (`PER_STORE_DELIVERY_FEE`) all now force a trusted 0. Worse, the actively-used `isAdminAuthenticated()` (gates every admin route) called the dead `getAccessToken()` as its *first* check on every single auth check — guaranteed to always return `null` (nothing ever populates the `adminAccessToken`/`adminTokenExpiry` sessionStorage keys it reads), so this ran on every page load for zero benefit before falling through to the real `adminToken`-based check. **Fixed 2026-07-27** by deleting the entire dead Edge Function login/refresh path and simplifying `isAdminAuthenticated()` down to just the real, working session-row-validated check; kept the three genuinely-used exports (`getCurrentAdmin`, `secureAdminLogout`, `isAdminAuthenticated`) in place, unchanged in behavior. The Supabase Edge Function source itself (`supabase/functions/admin-auth`) was left untouched — out of scope, a separate concern from the dead frontend code that could never reach it. Verified via `tsc --noEmit` clean on the admin panel and a full `vite build`; not click-tested live.

## Reference: Pricing Model / GST

Confirmed by product owner, 2026-07-16. Two independent, stacking GST layers — needed context for anything touching prices, checkout totals, or invoices:

1. **Per-item GST**, baked into each product's sellable price: `item_price = master_products.discounted_price + (discounted_price × master_products.gst_rate / 100)`. `discounted_price` is the pre-tax base. `is_loose = true` (loose/weighed products) → `gst_rate` is always 0. `is_loose = false` (packaged products) → follow the `gst_rate` column. Reference implementation: `frontend/src/utils/priceGst.ts`, mirrored in `admin/src/utils/priceGst.ts` and `frontend/src/services/supabase.ts:206-221`.
2. **A separate flat 5% GST on the whole bill at checkout**, mandated by GoI as a business-level tax (the rate can change if GoI changes it) — applied on top of the already-GST-inclusive item subtotal. This is intentional, not double taxation (see Confirmed Not Bugs below). Implemented in `frontend/src/utils/checkoutCalculations.ts`.

Any server-side price/total recomputation must replicate both layers or it will silently diverge from what the customer actually saw and agreed to pay.
